# RIP: как работает протокол динамической маршрутизации

RIP (Routing Information Protocol) — простой внутренний протокол динамической маршрутизации семейства distance-vector. Маршрутизаторы сообщают соседям, какие сети им известны и какова стоимость пути до каждой сети.

RIP выбирает путь по метрике, обычно равной количеству переходов между маршрутизаторами — hop count. Рабочие значения метрики находятся в диапазоне от 1 до 15, а 16 означает, что сеть недоступна.[1][2]

RIP полезен для обучения, лабораторных стендов и небольших стабильных сетей. Для крупных сетей он обычно не подходит из-за ограничения в 15 переходов и сравнительно медленной сходимости.

## Основная идея

Каждый RIP-маршрутизатор хранит для известных сетей как минимум:

- адрес и маску или длину префикса сети назначения;
- следующий маршрутизатор — next hop;
- метрику пути;
- интерфейс, через который доступен next hop;
- таймеры актуальности маршрута.

Маршрутизатор периодически передает соседям известные маршруты. Сосед увеличивает полученную метрику на стоимость входящего интерфейса, обычно на единицу, и сравнивает новый путь с уже известным.

Упрощенная логика выглядит так:

```text
Новая метрика = метрика, объявленная соседом + стоимость пути до соседа
```

При стандартной стоимости интерфейса `1` это превращается в подсчет переходов.

RIP основан на идеях алгоритма Беллмана—Форда: маршрутизатор не знает всю топологию сети, а принимает решение на основании информации от непосредственных соседей.

## Пример распространения маршрута

```text
192.168.10.0/24
       |
      R1 -------- R2 -------- R3
                              |
                       192.168.30.0/24
```

Пусть сеть `192.168.30.0/24` подключена к R3.

1. R3 объявляет эту сеть R2 с метрикой `1`.
2. R2 добавляет стоимость перехода и сохраняет маршрут с метрикой `2` через R3.
3. R2 объявляет маршрут R1.
4. R1 сохраняет путь до сети с метрикой `3` через R2.

Упрощенные таблицы:

```text
R3:
192.168.30.0/24  directly connected  metric 1

R2:
192.168.30.0/24  via R3             metric 2

R1:
192.168.30.0/24  via R2             metric 3
```

Способ отображения напрямую подключенного маршрута зависит от реализации: операционная система может показывать его как connected-маршрут с собственной административной метрикой, а RIP будет объявлять соседу RIP-стоимость.

## Как выбирается маршрут

Если несколько соседей объявили одну сеть, RIP предпочитает маршрут с меньшей метрикой.

```text
Через R2: метрика 3
Через R4: метрика 5

Выбран путь через R2.
```

При одинаковой метрике реализация может установить несколько равных маршрутов и распределять трафик между ними.

RIP не измеряет доступную пропускную способность, текущую задержку, надежность или загрузку канала. Поэтому путь через два медленных соединения может быть выбран вместо пути через три быстрых соединения. RFC также отмечает, что фиксированная метрика RIP не предназначена для выбора маршрута по параметрам реального времени.[3]

## Метрика и значение 16

Максимальная допустимая метрика RIP — `15`. Значение `16` зарезервировано как infinity — недостижимая сеть.[1][2]

Это ограничивает размер RIP-домена:

```text
1–15  — сеть достижима;
16    — сеть недостижима.
```

Небольшое значение infinity ускоряет остановку ошибочного роста метрики, но делает RIP непригодным для сетей, где путь может проходить более чем через 15 RIP-маршрутизаторов.

## Обмен маршрутами

### Периодические обновления

Маршрутизатор отправляет соседям полную RIP-таблицу примерно каждые 30 секунд. Если обновления от текущего next hop не приходят 180 секунд, маршрут признается недействительным.[2]

Периодическая схема проста, но имеет недостатки:

- таблица передается даже без изменений;
- изменения распространяются не мгновенно;
- потеря маршрута может некоторое время оставаться незамеченной;
- в большой таблице создается лишний служебный трафик.

### Triggered update

При существенном изменении маршрута RIP может отправить triggered update — внеочередное обновление без ожидания следующего 30-секундного цикла.

Например, после потери connected-сети маршрутизатор объявляет ее с метрикой `16`. После отправки triggered update запускается случайный интервал ограничения частоты; изменения, возникшие до его завершения, объединяются в следующее обновление. Это снижает риск шторма сообщений.

## Таймеры

Типичные таймеры RIPv2 по RFC 2453:[2]

| Таймер | Типичное значение | Назначение |
| --- | ---: | --- |
| Update | 30 секунд | Периодическая отправка таблицы маршрутов |
| Timeout | 180 секунд | Признание маршрута недействительным без обновлений |
| Garbage collection | 120 секунд | Время хранения недействительного маршрута перед удалением |
| Triggered update cooldown | 1–5 секунд | Ограничение частоты после отправки triggered update; накопленные изменения объединяются |

Это стандартные значения из RFC 2453. Конкретная реализация или конфигурация маршрутизатора может использовать другие значения, поэтому их нужно сверять с документацией системы.

В документации некоторых вендоров также встречается hold-down timer, часто около 180 секунд. Он временно ограничивает принятие подозрительных альтернатив после отказа маршрута. Hold-down не следует считать отдельным обязательным таймером для любой реализации RIP.

## Медленная сходимость

Сходимость — состояние, при котором все маршрутизаторы имеют согласованное представление о доступных маршрутах.

После отказа сети информация должна пройти от одного соседа к другому. До завершения процесса разные маршрутизаторы могут одновременно хранить старые и новые сведения. Из-за периодических обновлений и распределенного характера distance-vector RIP сходится медленнее современных link-state протоколов.

## Routing loop и count to infinity

Упрощенный пример ниже предполагает, что split horizon и poison reverse отключены. При обычном split horizon описанная двухмаршрутизаторная петля была бы предотвращена.

Предположим, сеть за R3 стала недоступна:

```text
R1 -------- R2 -------- R3 ---- X ---- 192.168.30.0/24
```

Возможная последовательность:

1. R3 теряет сеть.
2. R2 еще хранит прежний маршрут через R3.
3. R1 продолжает объявлять R2, что знает путь до этой сети.
4. R2 ошибочно принимает путь через R1.
5. R1 и R2 начинают ссылаться друг на друга.

Пакеты могут ходить по кругу, а метрика — увеличиваться при каждом обмене:

```text
3 → 4 → 5 → ... → 16
```

Такое постепенное увеличение называется count to infinity. Когда метрика достигает `16`, сеть признается недоступной.

## Защита от петель

### Split horizon

Маршрут не объявляется обратно через интерфейс, с которого он был изучен.

Если R2 узнал маршрут от R3, нет смысла сообщать R3, что путь к этой сети существует через R3 же.

### Route poisoning

При потере сети маршрут не удаляется молча, а объявляется с метрикой `16`.

```text
192.168.30.0/24  metric 16
```

Соседи быстрее узнают, что прежний путь использовать нельзя.

### Poison reverse

Маршрут объявляется обратно источнику, но с метрикой `16`. В RFC 2453 этот механизм называется split horizon with poisoned reverse: маршрут, полученный от соседа, включается в обновление этому соседу как недостижимый.[2]

### Triggered updates

Изменение отправляется сразу после отказа, а не только по периодическому таймеру.

### Hold-down

Реализация может временно не принимать ухудшившиеся или противоречивые объявления, пока информация об отказе распространяется по сети.

Эти механизмы снижают вероятность и продолжительность петель, но не превращают RIP в быстро сходящийся протокол для крупной сети.

## RIPv1, RIPv2 и RIPng

| Характеристика | RIPv1 | RIPv2 | RIPng |
| --- | --- | --- | --- |
| Сетевой протокол | IPv4 | IPv4 | IPv6 |
| Передает маску/префикс | Нет | Да | Да, IPv6 prefix length |
| Маршрутизация | Classful | Classless, CIDR/VLSM | Classless IPv6 |
| Доставка обновлений | IPv4 broadcast | Периодически обычно multicast `224.0.0.9`; возможны broadcast/unicast | Multicast `FF02::9` |
| Транспорт | UDP | UDP | UDP |
| Порт | 520 | 520 | 521 |
| Метрика infinity | 16 | 16 | 16 |
| Аутентификация | Нет | Есть поля аутентификации | В самом сообщении RIPng не предусмотрена |

### RIPv1

RIPv1 не передает маску подсети вместе с маршрутом. Получатель вынужден выводить маску из классовой адресации и локального контекста. Из-за этого RIPv1 не подходит для VLSM и разрывных сетей с неодинаковыми масками.

RIPv1 работает через UDP-порт `520`.[1]

### RIPv2

RIPv2 добавляет:

- маску подсети;
- поле next hop;
- route tag;
- поддержку аутентификации;
- classless-маршруты и VLSM;
- multicast-доставку периодических обновлений.

Для периодических RIPv2-обновлений зарезервирован multicast-адрес `224.0.0.9`, благодаря чему сообщения не приходится обрабатывать каждому IPv4-узлу сегмента.[2] Ради совместимости multicast можно отключить; на отдельных типах сетей и для ответов на запросы также применяется broadcast или unicast.

### RIPng

RIPng адаптирует RIP для IPv6. Он работает через UDP-порт `521` и отправляет обычные и triggered updates группе `FF02::9`.[3]

Основная логика distance-vector сохраняется: RIPng использует метрики от `1` до `15`, а `16` означает недостижимый маршрут.[3]

## Формат обмена на практике

RIP использует два основных типа сообщений:

- Request — запрос всей таблицы или отдельных маршрутов;
- Response — ответ на запрос либо периодическое или triggered update.

При запуске маршрутизатор может запросить таблицу у соседей, а затем поддерживает ее периодическими Response-сообщениями.

Маршрут из RIPv2 Response содержит, среди прочего:

```text
Address Family Identifier
Route Tag
IP Address
Subnet Mask
Next Hop
Metric
```

## Где RIP уместен

Преимущества RIP в небольшой сети:

- простая модель и сравнительно простая настройка;
- небольшое количество параметров;
- не требуется знание полной топологии;
- удобно наблюдать и изучать работу distance-vector маршрутизации.

Эти преимущества относятся именно к небольшому домену. Периодическая передача таблицы и медленная сходимость становятся недостатками по мере роста сети.

RIP можно использовать:

- в учебной лаборатории;
- в небольшой изолированной сети;
- в простом стенде с несколькими маршрутизаторами;
- для знакомства с distance-vector маршрутизацией.

RIP обычно не выбирают:

- для крупной сети;
- при наличии длинных маршрутов;
- когда нужна быстрая сходимость;
- когда путь нужно выбирать с учетом bandwidth или delay;
- в качестве внешнего протокола между автономными системами.

## Диагностика

Названия команд зависят от операционной системы или вендора, но проверять нужно одни и те же данные:

1. Активирован ли RIP на нужных интерфейсах и приходят ли обновления от ожидаемых соседей.
2. Приходят ли UDP-пакеты на порт `520` или `521`.
3. Какие сети объявляются.
4. Какой next hop и metric установлен для маршрута.
5. Не достигла ли метрика значения `16`.
6. Не блокируется ли multicast или broadcast.
7. Совпадают ли версия RIP и настройки аутентификации.

Пример пассивного просмотра RIPv2-трафика:

```bash
sudo tcpdump -ni any 'udp port 520'
```

Для RIPng:

```bash
sudo tcpdump -ni any 'udp port 521'
```

`tcpdump` только наблюдает трафик, но для запуска обычно нужны повышенные права.

## Краткая шпаргалка

```text
Тип протокола:       distance-vector
Алгоритмическая идея: Беллман—Форд
Основная метрика:    hop count
Допустимые метрики:  1–15
Недоступный маршрут: 16
Update timer:        обычно 30 секунд
Timeout:             обычно 180 секунд
RIPv1/RIPv2:         UDP 520
RIPv2 multicast:     224.0.0.9
RIPng:               UDP 521
RIPng multicast:     FF02::9
```

Главная идея RIP:

> Сообщай соседям известные сети и стоимость пути до них, а сам выбирай предложение с наименьшей метрикой.
